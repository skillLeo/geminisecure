Master prompt · paste as-is 
ROLE
You are the lead engineer implementing GeminiSecure, a multi-tenant SaaS platform for
gated communities and private security companies operating in Jamaica. I am attaching
39 HTML wireframe files and one build specification. Read all of them before writing code.

WHAT THIS PRODUCT IS
Gemini Security Limited is a Jamaican security company. It sells GeminiSecure as a
subscription to gated communities ("estates"). The platform has four user-facing
surfaces and two distinct tenant types, and the tenant boundary is the single most
important rule in the system:

  1. SUPER ADMIN CONSOLE (web, 1440px)  — Gemini Security's own staff. Sees ALL estates.
  2. COMMUNITY ADMIN CONSOLE (web, 1440px) — ONE estate's committee and property manager.
                                             Sees only that estate.
  3. RESIDENT APP (mobile, 433x892)     — a household inside one estate.
  4. GUARD APP (mobile, 433x892, dark)  — a security officer on shift at a post.

An estate's committee must never see another estate's data. A guard must never see a
resident's financial position. Gemini Security staff see operational data across all
estates but never a community's internal governance records. Enforce this at the
database layer with row-level security keyed on tenant_id — never in application code
alone, and never from a request parameter. Resolve tenant from the authenticated
session or the subdomain, never from user input.

NON-NEGOTIABLE DESIGN FIDELITY
The wireframes are the visual specification and they are already approved. Do not
redesign, do not "improve", do not substitute a component library.
  - Extract the :root token block from any wireframe file. Use those exact hex values.
    Never introduce a colour that is not in that block.
  - Fonts are Poppins (500/600/700) for display and Inter (400/500/600/700) for
    interface. IBM Plex Mono only where the wireframes use it. No other fonts.
  - The brand mark is TWO OVERLAPPING CIRCLES: viewBox 0 0 40 40, both r=12.5, cx=15
    and cx=25, with mix-blend-mode:multiply on the right circle. It is not a shield,
    not a padlock, not a monogram. Copy the SVG verbatim from the wireframes.
  - Icon stroke weights are contextual and not interchangeable: 1.8 sidebar nav,
    1.7 KPI tiles, 1.6 activity rows and input glyphs, 1.5 settings cog.
  - Radii: 10px controls, 12px inputs, 16px cards, 20px modals, 100px pills,
    48px phone screen. Shadows are copied verbatim, never invented.
  - Semantic colour is LOCKED and never themed: success #16A34A, danger #B91C1C,
    warning amber. A tenant may theme navy and amber; a tenant may never make
    "denied" look like "verified".

HOW TO WORK
Build in this order, and do not start a surface before the one above it works:
  1. Auth, tenancy, RLS policies, role matrix.        (foundation for everything)
  2. Super Admin Console — estates, guards, dispatch. (Gemini's own operations)
  3. Guard App — clock-in, scan, patrol, offline.     (the riskiest flows)
  4. Community Admin Console — dues, ledger, payroll. (the money)
  5. Resident App — passes, dues, voting.             (highest user count)

For every screen: match the wireframe exactly, then wire the behaviour described in
the build specification. If a behaviour is not specified, ask me — do not invent a
business rule, especially for money, restriction, biometrics or voting.

THINGS THAT WILL FAIL REVIEW
  - Any colour, font, radius or shadow not present in the wireframes.
  - A redrawn logo.
  - Tenant filtering done only in application code.
  - A guard-facing screen that displays an amount owed.
  - A ballot record that can link a vote to a voter.
  - An edited or deleted posted journal, gate event, or approved payroll run.
  - Statutory payroll rates hardcoded in application logic instead of a versioned
    rate table.

Open items requiring a client decision

Statutory payroll rates are unverified
The rates and totals shown on every payroll and payslip screen are structurally correct — NIS is deducted before Education Tax and PAYE, and the PAYE threshold is applied as a threshold rather than a flat percentage — but they have not been reconciled against current TAJ tables. Build the rate engine as a versioned table with an effective date. Do not go live on these numbers until the client's accountant signs them off.
Biometric consent wording needs legal review
The guard app enrols fingerprint and face, and performs on-device alertness checks. The consent screens exist in the wireframes but the wording is a draft. Legal review under Jamaican privacy expectations is a launch blocker for that feature only — build it behind a feature flag that ships disabled.
Payment gateway is not yet provisioned
Merchant onboarding in the Caribbean routinely takes longer than the software. Manual cash recording by the property manager is the day-one collection path and is fully specified. Build card capture behind an adapter interface so the gateway can be dropped in later without touching the dues screens.
No public marketing or legal pages exist
The approved set covers the four authenticated surfaces only. A public landing page, privacy notice, terms of service, biometric consent policy and data retention schedule are not in the wireframes. They are needed before launch but are not part of this build.
